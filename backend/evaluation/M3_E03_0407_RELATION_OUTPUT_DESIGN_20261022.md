# M3 E03 设计：0407关联覆盖与双列输出

日期：2026-10-22。状态：来源核查与本地正反例已完成，见 [独立核查记录](M3_E03_0407_SOURCE_AND_LOCAL_TEST_REVIEW_20261022.md)；随后发现的冻结 SQLite 外键与结构注解见 [版本绑定核查](M3_E03_0407_VERSION_BOUND_RELATION_REVIEW_20261022.md)，它修正了本设计中“缺少独立归属依据”的初始判断，但不消除孤儿记录。候选关系与输出提示已按 [2026-10-23 本地实施记录](M3_E03_0407_LOCAL_IMPLEMENTATION_20261023.md)以独立开关接入，尚未运行新的服务器对照。E02 的1479已按 [人工审查记录](M3_E02_PAIR24_ACCEPTANCE_REVIEW_20261022.md)确认；0407不得混入1479的已通过结论。

## 1. 公开需求与已观察失败

`BIRD-PG-0407` 的公开 question 是“Lists all types of cards in German.”；evidence 写明 German 是语言，all types 指 `subtypes`、`supertypes`，且两列均不为 NULL。授权字段中已有 `cards.subtypes`、`cards.supertypes` 和 `foreign_data.language`；本轮20个选择名额已用满，却没有 `cards.uuid`、`foreign_data.uuid`。E02基线和候选生成相同的一列 SQL：`foreign_data.type`，`language='German'`，并要求该错误列非空。保存结果为2150行、1列；冻结参考执行为1693行、2列（按既定原生元组集合比较仍不匹配）。

`cards.uuid` 在源结构有唯一索引，`foreign_data.uuid` 类型同为 TEXT；两表未声明这条外键，`foreign_data.uuid` 的公开描述也没有显式指向 `cards`。冻结数据中子表229,186行、229,170行能匹配父表，另有16条孤儿记录，其中德语记录3条。现有 E02 `relation_candidates` 将其标为 `incomplete_child_key_coverage`、`eligible=false`，因此既不提供自动连接边，也没有补两端键。上述统计是来源绑定的离线审查证据；上线前仍需当前服务器来源验证，不能把它写成数据库约束或证明连接类型。

## 2. 两项独立假设

### A. 有边界的关系上下文

“存在孤儿”应阻止声明完整参照或无损连接，却不必抹去已审查的键统计。拟把关系状态拆为：`declared_fk`、`reviewed_complete_candidate`、`reviewed_incomplete_candidate`、`diagnostic_unresolved`、`rejected`。0407目前还缺独立的字段归属说明，先停在 `diagnostic_unresolved`。只有补足不依赖 Gold 的官方结构／字段语义依据，并再次核对当前来源、权限和数据版本后，才允许升级为 `reviewed_incomplete_candidate`，供模型判断公开问题中的“cards with German records”是否需要关联。升级后仍需保留 `orphan_rows=16`、`German_orphan_rows=3`、未声明外键、未证明语义等价及未预设 JOIN 类型等事实。候选关系不能自动改 SQL，也不能使样本值变成强制谓词。若存在多个同等合理路径、授权不足或实时来源不匹配，则只报告歧义或拒绝，不选边。

如果上述关系审查通过，关系展示必须携带两端 `uuid`。在原20字段额度内，先保护公开指定的两个输出字段和语言筛选字段，再为已选择的关系预留两端键；如需腾出2个名额，只从未承担公开输出、筛选或已确定关系角色的其余字段中按原检索顺序确定性淘汰。记录被移除字段、原因和原分数。不能静默把20改为22，不能依 case_id 写特殊分支；名额不够则明确 `context_field_cap`，不声称已提供可执行关联。

这一策略还必须区分连接覆盖与结果总体。德语孤儿行没有对应卡牌，公开问题若以“cards”为主体，INNER JOIN 是可检验的解释，但不能因为冻结 Gold 使用 INNER JOIN 就把这种解释硬编码。NULL、孤儿、重复子行及多个关系路径都应在上下文或审查记录中可见。

### B. 公开 evidence 的输出字段组

将 `all types` 与 evidence 中明确给出的 `subtypes`、`supertypes` 绑定为一个**有顺序的双列输出组**，并记录“两列均非 NULL”的公开约束。模型提示应区分：投影来自 `cards` 的这两列，`German` 是 `foreign_data.language` 的筛选；`foreign_data.type` 虽与 types 字面相近，却不是 evidence 指定的输出列。字段组仅由公开 question/evidence 和授权 catalog 建立，不读取 Gold SQL 或答案。

先以报告型观察验证提示的识别、投影和 NULL 条件；不要同时升级为全局硬拒绝或增加修复轮次。对“only one type”“exclude supertype”“all card types without language qualifier”等反例应保留原意，不能一律强加双列或德语筛选。无法唯一定位列归属或存在冲突时记录未解析，不猜测。

## 3. 实施顺序与检查点

1. **本地来源审查**：固定0407公开输入、两端字段授权、唯一索引、16条孤儿及德语3条的证据摘要；核实 E02 报告的20列和当前拒绝原因。另查官方结构／字段说明能否独立支持 `foreign_data.uuid` 的卡牌归属；证据不足时只保留诊断，不向模型展示可用连接边。禁止用 scorer/Gold 决定提示或连接规则。
2. **关系表达与额度决策**：增加不完整候选的独立状态和说明，不改变声明外键语义；加入确定性的字段保护／腾挪诊断。先做无模型的正反例和同来源离线回放，确保1479原有5列及其关系仍成立，20道成功回归题的授权字段不受无关影响。
3. **输出组提示与观察**：仅对公开 evidence 明确解析的字段组提供提示，输出字段和非空要求分别可追溯；记录生成 SQL 实际投影、筛选及连接。先保持原 SQL 校验、修复次数、模型预算和原生评分不变。
4. **独立服务器实验**：冻结新代码、索引、24题题单、模型与预算，在新目录做一次基线／候选同轮对照；两边各自建索引，先完成捕获再独立无模型原生复评。重点检查0407是否真正使用 `cards.subtypes`、`cards.supertypes`、`foreign_data.language` 及有依据的连接，不能仅凭原生结果相等判断策略合理。

为区分因果，服务端对照前应先有本地消融：仅关系上下文、仅输出组提示、两者同时开启。若只部署最终组合，也必须在报告中分别记录两类上下文及模型采纳情况，不把改善归因于其中单项。

## 4. 必须覆盖的正反例

- 正例：同来源、父键唯一、类型一致、有独立归属依据且存在已记录孤儿时，可展示“非完整候选”，不能写成声明外键；公开问题要求跨表筛选且键在额度内时补两端键并记录腾挪。
- 反例：只有相同字段名、类型和键值覆盖统计，却没有独立归属依据时，保持 `diagnostic_unresolved`，不得向模型宣称可用连接边。
- 正例：公开 evidence 将含糊的 `all types` 明确指定为两列时，提示保留字段顺序和两列非空约束。
- 反例：跨数据库、来源/版本/角色不匹配、父键不唯一、键类型不兼容或未授权列，拒绝候选关系。
- 反例：多个可选关系、孤儿记录或NULL不能触发自动 INNER JOIN、修补数据或声称无损。
- 反例：20字段额度无法安全腾挪时，保留原字段并报告不足；不得越界或丢掉公开条件。
- 反例：公开 question 对输出有 only/exclude 指令、evidence 含冲突解释或字段组归属不唯一时，不强制双列。
- 回归：1479币种条件和关系维持；20道既有成功题不出现新误拒绝；0050、0085不通过改评分或改Gold“修复”。

## 5. 预登记验收边界

下一轮的主目标是0407的公开语义和独立原生匹配都成立；20道成功回归题全部保留，模型 HTTP、含索引 token 和逐题 p95 均有记录且候选不超过同轮基线120%。保留 E02 的预算上限、隔离、来源校验和无模型复评。若任一关键字段或关系依据缺失，实验应报告未覆盖，不以人工补写 SQL、增加生成次数或更换题单追分。
