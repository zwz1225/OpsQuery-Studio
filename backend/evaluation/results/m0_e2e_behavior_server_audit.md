## 两处独立问题

1. **澄清路径未进入结构化暂停。** 起点走 `direct_response/completed`，`trace.clarification=null`。恢复用例因此立即失败。当前报告没有 `message`、`analysis`、`route_reason`，无法区分“普通文本澄清”和完全未澄清；应先补充观察字段，再决定是调整预期、换一个确实需要工作流澄清的问题，还是修复路由。
2. **空结果与日期口径。** Gold SQL 使用 `[1900-01-01, 1900-01-02)`，生成 SQL 却使用 `[1900-01-01, 1900-02-01)`，把一天扩大为一个月。两条 SQL 在当前数据上都返回 0 行、列也相同，说明只比较空行结果会漏掉时间条件错误。服务器 trace 显示工具调用成功、0 行、无 SQL 错误，服务最终却为 `failed`。从代码路径看，这与结果整理阶段返回 `valid=false` 一致；报告未记录该阶段的原因，不能确定它是否因日期错误或空结果而拒绝。

当前 `sql_case_count=3` 按最终路由为 `database_query` 计数，包含空结果失败和受控故障；它不是实际执行成功的 SQL 数。空结果题的 `sql_execution_success=false` 也来自“服务已完成且有 SQL”的现有定义，而 trace 显示底层 SQL 确实执行成功。后续分析须区分服务状态、工具执行和结果评分。
