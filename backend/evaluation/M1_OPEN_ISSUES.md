## 为什么 M1 用了多轮复验

1. **环境与来源准备有实际工作量。** 服务器无系统级 PostgreSQL 安装权限，改用用户目录的 PostgreSQL 16；M1 B 才能建立隔离库、导入 41 表并独立验证。C3 首次完整校验遭遇 `/home` 文件系统空间耗尽，报告未写成；清理空间后 v2 完成 24 项检查。这是已解决的运行环境问题，不能当作当前数据库内容错误。
2. **PostgreSQL 方言和业务约束需要真实执行验证。** 430 题 Gold 证明已编写 SQL 可在两后端执行且结果等价，但不能覆盖模型新生成的 SQL。v5 的 `CHANNEL_OPS-136` 在 `ORDER BY ABS(target_gap)` 内引用同层输出别名，服务器独立复现 `SQLSTATE 42703`；改写并补强校验后，v6/v7 执行成功。`CHANNEL_OPS-025` 的“截至某月”曾需修正日期约束识别，v7 已 PASS。两项均为已修复的历史问题。
3. **严格评分暴露持续变化的显示列名。** v5 一题、v6 两题以及 v7 三题的差异并非同一组稳定失败题；已核实的别名按题独立复评分并更新正式题集，每次旧报告都保留。v7 的七项候选仍未完成该流程。模型为何选不同显示列名尚无确定性根因证据；能确认的是当前评分契约与实际列名不匹配。
4. **验收目标混合了不同层次。** 数据源适配、Gold、live 结果值、严格列名、E2E 行为和回复质量各有独立证据。把 430/430 Gold 或 79/79 宽松结果写成“新 live 严格 79/79”，会掩盖真实缺口；把三个列名差异写成 PostgreSQL 数据迁移失败，也与完整行摘要、Gold 和 live 值证据不符。

因此建议 M1 以[有条件收尾记录](M1_FINAL_ACCEPTANCE.md)归档：功能和数据来源改造已验收，原始严格 79/79 保持未达；后续优先解决输出列名契约与回复质量，再按清晰的新门槛扩展评测。原始服务器 JSON、离线复评分和正式题集版本应分别保存，不能互相覆盖。
